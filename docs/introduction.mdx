# 什么是 Hile？

Hile 是一套面向 **Node.js** 的**轻量级服务化工具集**。它的名字源于"轻"的谐音，寓意让开发者用最轻量的心智负担构建服务端应用。

Hile 基于 **pnpm workspace monorepo**，所有包均为**纯 ESM + TypeScript** 编写，需要 Node.js >= 20.12 且在 `package.json` 中设置 `"type": "module"`。

## 为什么需要 Hile？

在 Node.js 后端开发中，你通常会遇到以下问题：

- **服务启动顺序难以管理**：数据库连接要在 HTTP 服务启动之前完成，Redis 要在使用缓存之前就绪。多个服务之间的启动顺序如何协调？
- **优雅关闭容易出错**：进程收到终止信号时，要先停止接受新请求，再关闭数据库连接，最后释放 Redis 连接——顺序错了就会丢数据或泄漏连接。
- **样板代码重复**：每次新项目都要写一样的服务启动代码、一样的数据库配置、一样的信号处理。
- **多进程通信成本高**：WebSocket、IPC、Worker Threads 各自有独立的 API，切换实现方式要重写大量代码。

Hile 用一个**服务容器**（`@hile/core`）统一解决这些问题。你只需要定义"服务是什么"和"关闭时该做什么"，容器自动处理依赖顺序、并发合并和优雅关闭。

## 谁应该使用 Hile？

- **Node.js 后端开发者**：需要快速搭建 REST API 或微服务
- **全栈工程师**：需要将 Next.js 和 API 服务运行在同一个端口上
- **微服务架构团队**：需要进程间通信（WebSocket / IPC / Worker Threads）和轻量级服务发现
- **希望减少样板代码的开发者**：Hile 用约定（文件系统路由、自动加载 boot 文件）代替配置

## 核心特性

<CardGroup cols={2}>
  <Card title="异步服务容器" icon="cube">
    全局单例容器，管理服务的注册（<code>register</code>）、解析（<code>resolve</code>）和优雅关闭（<code>shutdown</code>）。支持依赖图追踪、循环依赖检测、并发请求合并、启动/关闭超时控制。基于 Node.js <code>AsyncLocalStorage</code> 自动追踪服务间的依赖关系。
  </Card>
  <Card title="HTTP 服务框架" icon="server">
    基于 Koa + find-my-way（高性能树形路由器）。提供 <code>Http</code> 类，支持全局中间件（Koa 中间件）、手动路由注册（<code>get/post/put/delete</code>）、文件系统自动路由、Zod 校验（query / params / body）、全局响应插件链。
  </Card>
  <Card title="Next.js 集成" icon="react">
    将 Next.js 作为渲染引擎嵌入 Koa 服务，共享同一端口。API 路由与页面路由互不冲突——API 走 <code>/-/*</code> 前缀，页面走 Next.js 路由。支持开发模式热更新（HMR），自动处理静态文件服务。
  </Card>
  <Card title="命令行启动器" icon="terminal">
    一条 <code>hile start</code> 命令启动所有服务。自动扫描 <code>*.boot.ts</code> / <code>*.boot.js</code> 文件，内置彩色容器事件日志（开发模式），支持 <code>--env-file</code> 加载环境变量，支持优雅关闭（SIGTERM / SIGINT）。
  </Card>
  <Card title="数据库集成" icon="database">
    TypeORM DataSource 服务化封装——在容器中自动初始化数据库连接，关闭时自动销毁。提供 <code>createDataSource()</code> 手动创建和容器模式（default export）两种方式。内置事务辅助函数 <code>transaction()</code>，支持 LIFO（后进先出）补偿回调。通过环境变量配置，零代码连接数据库。
  </Card>
  <Card title="Redis 集成" icon="bolt">
    ioredis 客户端的服务化封装。提供 <code>createRedis()</code> 手动创建和容器模式两种方式。自动连接、自动断连、环境变量配置。只需一行 <code>auto_load_packages</code> 配置就能让 Redis 在容器中可用。
  </Card>
  <Card title="类型安全 Redis 缓存" icon="table">
    基于 <code>@hile/ioredis</code> 的缓存层。模板字符串键类型推导——例如 <code>defineCache('user:{id:string}:profile', fn)</code> 会推导出参数的类型。提供 <code>read</code>（读穿透）、<code>write</code>（强制回源）、<code>remove</code>（删除）、<code>has</code>（存在检查）四种操作。
  </Card>
  <Card title="消息通信体系" icon="message-square">
    抽象消息通信协议（REQUEST / RESPONSE / ABORT），支持 WebSocket、IPC、Worker Threads 三种传输实现。统一的 <code>_send()</code>（双向）、<code>_push()</code>（单向）、<code>_stream()</code>（流式）三种通信模式。同一套 API 切换底层传输方式——只需继承不同的抽象类。
  </Card>
  <Card title="轻量级服务发现" icon="map">
    基于 WebSocket 的 Registry 注册中心。Server/Client 模型，心跳检测，namespace 分组，topic 发布/订阅，断路器（Circuit Breaker，30 秒冷却期），连接缓存降级。适合中小规模微服务集群。
  </Card>
  <Card title="运行时动态配置" icon="toggle">
    基于 Redis 持久化 + Registry topic 发布/订阅的配置中心。Zod schema 校验配置结构，运行时修改配置后实时推送到所有订阅方。修改配置无需重启服务。
  </Card>
  <Card title="业务模型层" icon="layers">
    提供 <code>defineModel</code> 和 <code>loadModel</code> 定义业务逻辑。支持 Pipeline 中间件模式（类似 Koa 中间件链），可注入容器服务（自动 <code>loadService</code>）。分离"怎么做"（Model）和"怎么暴露"（Controller）。
  </Card>
  <Card title="定时任务调度" icon="clock">
    基于 <code>node-schedule</code> 的定时任务管理器。支持 cron 表达式和延迟执行两种模式。<code>Scheduler</code> 类管理任务，<code>defineJob</code> 定义任务。支持文件系统自动加载 <code>*.schedule.ts</code> 文件。
  </Card>
  <Card title="结构化日志" icon="file-text">
    基于 <code>pino</code> 的高性能日志器。<code>createLogger()</code> 创建实例。开发模式自动使用 <code>pino-pretty</code> 可读格式，生产模式输出 JSON 格式（适合日志收集系统如 ELK）。支持日志级别、字段脱敏（redact）配置。
  </Card>
  <Card title="简便脚手架" icon="wand">
    <code>npx create-hile create my-app</code> 交互式创建项目。内置 6 种模板（default / next / micro-http / micro / micro-http-next / monorepo），自动安装依赖。
  </Card>
</CardGroup>

## 包一览

Hile 目前包含 **19 个包**，分为以下几类：

### 核心框架包

| 包名 | 说明 | 安装命令 |
|------|------|----------|
| `@hile/core` | **异步服务容器**——Hile 的基石。`Container` 类管理服务的注册、解析、依赖追踪和优雅关闭。全局单例 `globalThis.HILE_GLOBAL_CONTAINER`。提供便捷函数 `defineService` / `loadService` / `isService`。 | `pnpm add @hile/core` |
| `@hile/loader` | **文件系统加载器抽象**——提供 `Loader` 抽象基类（子类实现 `bind` 方法），以及 `scanDirectory`、`compileRoutePath`、`toRouterPath`、`normalizePath` 等工具函数。被 `@hile/http` 和 `@hile/message-loader` 共同使用。 | `pnpm add @hile/loader` |
| `@hile/logger` | **结构化日志服务**——基于 pino 的日志器封装。导出 `createLogger()` 和默认的 `defineService`。 | `pnpm add @hile/logger` |
| `@hile/schedule` | **定时任务调度器**——基于 node-schedule。`Scheduler` 类管理任务，支持 cron 表达式和延迟执行。`defineJob` 定义任务，`Scheduler.load()` 从文件系统自动加载。 | `pnpm add @hile/schedule` |
| `@hile/model` | **业务模型层**——定义可复用的业务逻辑单元。`defineModel` / `loadModel` / `isModel`。支持 Pipeline 中间件，可注入容器服务（自动 `loadService`），类型安全。 | `pnpm add @hile/model` |

### HTTP 服务包

| 包名 | 说明 | 安装命令 |
|------|------|----------|
| `@hile/http` | **HTTP 服务框架**——`Http` 类（基于 Koa + find-my-way）。支持全局中间件（`use`）、手动路由（`get/post/put/delete/trace/patch/route`）、文件系统路由（`load`）、Zod 校验（`defineController` + `createControllerMetadata`）、全局响应插件链（`defineResponsePlugin`）。 | `pnpm add @hile/http` |
| `@hile/http-next` | **Next.js 桥接层**——`HttpNext` 类，将 Next.js 作为渲染引擎嵌入 Koa 服务。API 和 SSR 共享同一端口，控制器自动加载，内置静态文件服务。 | `pnpm add @hile/http-next` |

### 数据存储包

| 包名 | 说明 | 安装命令 |
|------|------|----------|
| `@hile/typeorm` | **TypeORM 集成**——`createDataSource()` 手动创建和 default export 容器模式。环境变量自动配置，支持 `transaction()` 事务辅助函数（带 LIFO 补偿回调）。 | `pnpm add @hile/typeorm` |
| `@hile/ioredis` | **Redis 集成**——`createRedis()` 手动创建和 default export 容器模式。环境变量自动配置，自动连接/断连。 | `pnpm add @hile/ioredis` |
| `@hile/cache` | **类型安全 Redis 缓存**——基于 `@hile/ioredis`。`defineCache` 定义缓存（模板键语法），`RedisCache` 类提供 `loadCache` 返回 `{read, write, remove, has}` 操作。 | `pnpm add @hile/cache` |

### 消息通信包

| 包名 | 说明 | 安装命令 |
|------|------|----------|
| `@hile/message-modem` | **消息通信抽象层**——`MessageModem` 抽象基类。定义 REQUEST / RESPONSE / ABORT 协议。提供 `_send()`、`_push()`、`_stream()`、`receive()`、`_dispose()` 方法。子类实现 `post()` 和 `exec()`。 | `pnpm add @hile/message-modem` |
| `@hile/message-ws` | **WebSocket 通信实现**——`MessageWs` 抽象类。基于 `ws` 模块，JSON 序列化/反序列化传输。构造时传入已连接的 WebSocket 实例。 | `pnpm add @hile/message-ws` |
| `@hile/message-ipc` | **Node.js IPC 通信实现**——`MessageIpc` 抽象类。基于 `child_process` 的 IPC 通道。支持父子进程双端使用。 | `pnpm add @hile/message-ipc` |
| `@hile/message-worker-thread` | **Worker Threads 通信实现**——`MessageWorkerThread` 抽象类。基于 `worker_threads` 模块。支持主线程和 Worker 线程双端使用。 | `pnpm add @hile/message-worker-thread` |
| `@hile/message-loader` | **文件系统消息路由加载器**——`MessageLoader` 类（继承 `Loader`）。`defineMessage()` 定义处理器，`register()` 手动注册，`dispatch()` 分发消息。使用 rou3 路由器。 | `pnpm add @hile/message-loader` |

### 微服务包

| 包名 | 说明 | 安装命令 |
|------|------|----------|
| `@hile/micro` | **轻量级服务发现与微服务框架**——包含 `Server`（WebSocket 服务端 + 消息路由）、`Client`（WebSocket 客户端 + 心跳）、`Registry`（注册中心 + topic 发布/订阅 + YAML 配置监听）、`Application`（集成 Registry 客户端 + 断路器 + 重试 + topic 管理）。 | `pnpm add @hile/micro` |
| `@hile/micro-dynamic-configs` | **运行时动态配置服务**——`MicroDynamicConfigsServer` 类。基于 Redis 持久化 + Registry topic 发布/订阅。Zod schema 校验配置结构，`save()` 方法写入 Redis 并实时推送变更，`on('change:key')` 监听配置变更。 | `pnpm add @hile/micro-dynamic-configs` |

### 开发工具包

| 包名 | 说明 | 安装命令 |
|------|------|----------|
| `@hile/cli` | **命令行启动器**——`hile start` 启动服务（自动加载 boot 文件），`hile registry` 启动注册中心，`hile registry configs` 管理配置。优雅关闭（SIGTERM/SIGINT 处理）。 | `pnpm add @hile/cli` |
| `create-hile` | **项目脚手架**——`npx create-hile create my-app` 交互式创建项目。内置 6 种模板，自动初始化项目结构和安装依赖。 | `pnpm create hile` |

所有包的完整版本号以 npm 最新发布版本为准。建议使用 `pnpm add @hile/core@latest` 等方式确保安装最新版本。

## 包依赖关系

以下是 Hile 各包的依赖关系图。箭头方向表示"依赖于"，即 A → B 表示"A 依赖于 B"。

### 核心依赖链

```
@hile/core                ← 基础容器，零外部依赖（仅依赖 Node.js 内置 AsyncLocalStorage）
  ├── @hile/cli           ← 启动器，依赖 core + micro（registry 命令）
  ├── @hile/logger        ← 日志，依赖 core + pino
  ├── @hile/typeorm       ← 数据库，依赖 core + typeorm
  └── @hile/ioredis       ← Redis，依赖 core + ioredis
       └── @hile/cache    ← 缓存，依赖 ioredis + core
```

### HTTP 依赖链

```
@hile/loader              ← 文件系统加载器抽象 + 工具函数（scanDirectory, compileRoutePath 等）
  ├── @hile/http          ← HTTP 框架，使用 @hile/loader 的工具函数
  │     └── @hile/http-next ← Next.js 桥接，依赖 http + next + koa-static
  └── @hile/message-loader ← 消息路由加载器，继承 Loader 抽象类
```

### 消息通信依赖链

```
@hile/message-modem       ← 抽象协议层，零外部依赖
  ├── @hile/message-ws    ← WebSocket 实现，依赖 message-modem + ws
  ├── @hile/message-ipc   ← IPC 实现，依赖 message-modem（零外部依赖）
  └── @hile/message-worker-thread  ← Worker 实现，依赖 message-modem

@hile/loader              ← 文件扫描与路径编译
  └── @hile/message-loader ← 消息路由加载器，继承 Loader + rou3
       └── @hile/micro     ← 微服务框架，继承 message-loader + ws
            ├── Registry   ← 注册中心（继承 Server），依赖 yaml
            └── Application ← 微服务应用节点（继承 Server）
                 └── @hile/micro-dynamic-configs ← 动态配置，依赖 micro + ioredis + zod
```

## 典型技术栈组合

根据你的项目类型，选择不同的包组合：

<AccordionGroup>
  <Accordion title="纯 API 服务（最简组合）">
    **适用场景**：REST API、微服务后端、BFF（Backend For Frontend）

    **安装命令**：
    ```bash
    pnpm add @hile/core @hile/http @hile/cli
    ```

    **组合说明**：
    - `@hile/core` 提供服务容器，管理生命周期
    - `@hile/http` 提供 HTTP 服务（路由、中间件、控制器）
    - `@hile/cli` 提供命令行启动（自动加载 boot 文件、优雅关闭）

    **典型目录结构**：
    ```
    my-api/
    ├── src/
    │   ├── services/
    │   │   └── http.boot.ts     # 服务入口（定义 Http 服务）
    │   └── controllers/
    │       └── users.controller.ts
    ├── package.json
    └── tsconfig.json
    ```
  </Accordion>
  <Accordion title="API + 数据库 + 缓存">
    **适用场景**：需要数据库和 Redis 缓存的后端服务

    **安装命令**：
    ```bash
    pnpm add @hile/core @hile/http @hile/cli @hile/typeorm @hile/ioredis @hile/cache
    ```

    **组合说明**：
    - 所有资源通过容器统一管理生命周期
    - 数据库连接在容器启动时自动初始化
    - Redis 在服务关闭时自动断连

    **自动加载配置**（在 package.json 中）：
    ```json
    {
      "hile": {
        "auto_load_packages": ["@hile/typeorm", "@hile/ioredis"]
      }
    }
    ```
  </Accordion>
  <Accordion title="全栈应用（API + Next.js SSR）">
    **适用场景**：包含前端页面的全栈应用

    **创建方式**：
    ```bash
    npx create-hile create my-app
    ```
    在 CLI 交互中选择 **`next`** 模板或 **`micro-http-next`** 模板。

    **组合说明**：
    - Koa API 路由与 Next.js 页面共享同一端口（3000）
    - API 路由默认前缀为 `/-`（如 `/-/post`）
    - Next.js 页面路由不受影响（如 `/`、`/about`）
    - 开发模式支持 Next.js HMR（热模块替换）
    - 静态文件由 koa-static 自动服务

    **关键架构决策**：为什么 API 路由要加前缀 `/-`？因为 Next.js 会接管所有它认识的路由（基于 `app/` 或 `pages/` 目录），给 API 路由一个特殊前缀可以避免路由冲突。HttpNext 先加载 API 路由（`/-/*`），最后才把 Next.js handler 挂载为兜底中间件。
  </Accordion>
  <Accordion title="消息服务 / 微服务发现">
    **适用场景**：多进程之间用 WebSocket 做请求/响应通信，需要服务发现

    **安装命令**：
    ```bash
    pnpm add @hile/message-loader @hile/message-ws @hile/micro
    ```

    **组合说明**：
    - `@hile/message-loader` 从文件系统加载消息处理器
    - `@hile/message-ws` 提供 WebSocket 传输层
    - `@hile/micro` 的 Registry 作为注册中心，Application 作为微服务节点

    **典型架构**：
    ```
    Registry (注册中心，9876 端口)
      ↑ WebSocket 连接
      ├── Application A (namespace: "user-service")
      │     └── 提供 /-/findUser 消息处理
      └── Application B (namespace: "order-service")
            └── 提供 /-/createOrder 消息处理

    A 通过 app.call("order-service", "/-/createOrder", data) 调用 B
    ```
  </Accordion>
  <Accordion title="运行时动态配置">
    **适用场景**：需要配置中心、配置修改后实时推送到所有服务的微服务集群

    **安装命令**：

    ```bash
    pnpm add @hile/micro @hile/micro-dynamic-configs ioredis zod
    ```

    **组合说明**：
    - `MicroDynamicConfigsServer` 基于 Zod schema 校验配置
    - Redis 持久化配置值
    - 配置变更通过 Registry topic 发布/订阅实时推送

    **工作流程**：
    1. 调用 `configServer.save({ featureX: true })`
    2. 配置被写入 Redis 持久化
    3. 同时通过 `app.publish()` 发布到 Registry
    4. Registry 推送给所有订阅了该 topic 的服务
    5. 订阅方通过 `on('change:featureX', callback)` 感知变更
  </Accordion>

## 设计哲学

### 1. 服务即单例（按 key 保证）

通过 `defineService(key, fn)` 定义的服务，由容器按**服务 key**（一个字符串或 Symbol）保证全局唯一。无论你在多少个地方 `loadService()` 同一个服务的注册信息，容器只会执行一次工厂函数 `fn`，后续调用都返回缓存的同一个实例。

```typescript
const dbService = defineService('database', async (shutdown) => {
  const connection = await createConnection()
  shutdown(() => connection.destroy())
  return connection
})

// 无论 loadService 多少次，返回的都是同一个 connection 实例
const db1 = await loadService(dbService)
const db2 = await loadService(dbService)
console.log(db1 === db2) // true
```

### 2. 约定优于配置

Hile 大量使用约定来减少样板代码：

- **文件系统路由**：`src/controllers/users.controller.ts` 自动映射到 `GET /users`（前缀可配）。不需要路由配置文件。
- **自动加载 boot 文件**：CLI 自动扫描 `src/**/*.boot.ts`（开发模式）或 `dist/**/*.boot.js`（生产模式）并加载。
- **环境变量配置**：`@hile/typeorm` 和 `@hile/ioredis` 从环境变量读取配置。不需要额外的配置文件。
- **自动加载包**：在 `package.json` 的 `hile.auto_load_packages` 数组中声明包名，CLI 自动 import 并 `loadService`。

### 3. 优雅关闭

每个服务通过 `shutdown` 回调注册清理函数。当进程收到 SIGTERM/SIGINT 信号时，容器按**后注册的先关闭**（LIFO）顺序执行所有 shutdown 回调。

### 4. 可观测性

容器事件流覆盖服务全生命周期：`service:init` → `service:ready` / `service:error` → `service:shutdown:start` → `service:shutdown:done` / `service:shutdown:error`。在开发模式下，CLI 自动订阅这些事件并以彩色日志输出。

### 5. 渐进式采用

你不需要一次性使用所有 Hile 包。可以从只用 `@hile/core` 管理服务开始，逐步添加 HTTP、数据库、缓存、消息通信等能力。每个包都可以独立使用。

### 6. 传输层与业务层分离

消息通信体系严格遵循接口分离：`MessageModem` 只定义协议，各传输实现（ws/ipc/worker-thread）只需实现 `post()` 和 `exec()` 两个方法。从 WebSocket 切换到 IPC 只需改继承的基类。

### 7. 最小依赖原则

- `@hile/core` 零外部依赖（只使用 Node.js 内置 API）
- `@hile/message-modem` 零外部依赖
- `@hile/message-ipc` 零外部依赖（只使用 Node.js 内置 `child_process`）
- `@hile/loader` 只依赖 `glob` 包
