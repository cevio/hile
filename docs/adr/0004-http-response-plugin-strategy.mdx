---
title: "ADR-0004: defineResponsePlugin 响应后处理策略"
description: "控制器结果的统一后处理机制"
---

## 背景

`@hile/http` 的 `defineController` 原本在控制器执行后直接将返回值写入 `ctx.body`。随着 HTTP 输出场景变复杂（统一响应包裹、按请求类型转换输出、特定路径定制化等），需要一个统一且可组合的"响应后处理层"。

分散在各控制器中会导致：

- 响应格式策略不一致
- 控制器职责膨胀，业务代码与协议层耦合
- 跨路由策略难以复用

## 决策

引入 `defineResponsePlugin` 作为控制器结果的统一后处理机制：

1. 控制器返回值先进入响应插件链，再决定最终 `ctx.body`
2. 插件函数签名：`(ctx, result, next) => Promise<any>`
3. 插件按注册顺序串行执行，onion-like 的 `next(transformedResult)` 传递
4. 最终结果 `!== undefined` 时才写入 `ctx.body`
5. 插件定位在"结果变换层"，不替代 Koa 全局中间件

## 影响

**正向：**

- 统一响应策略可集中管理、可复用
- 控制器保持"返回业务结果"的单一职责
- 便于扩展内容协商/包装/过滤等能力

**代价：**

- 插件链引入额外执行开销
- 插件顺序影响最终结果，需要治理与约定
- 插件误传 `undefined` 可能导致无响应体

## 约束

1. 插件应保持纯结果变换语义
2. 插件必须显式调用 `next(...)` 传递结果
3. 需要"吞掉响应体"时必须有明确注释与测试
4. 公共响应格式插件建议在框架初始化阶段集中注册

## 备选方案

1. **每个控制器手动包装返回值**：重复代码多，难统一演进
2. **仅使用 Koa 全局中间件处理 body**：难拿到控制器原始返回值语义
3. **defineController 内置单一固定包装规则**：扩展性差
